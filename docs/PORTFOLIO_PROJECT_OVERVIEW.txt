2. CORE PROBLEM & ARCHITECTURAL MOTIVATION
================================================================================

The Enterprise Agent Paradox:
Large Language Models (LLMs) excel at multi-step reasoning, planning, and tool calling.
However, enterprises cannot deploy unconstrained autonomous agents into production because
probabilistic models carry inherent risks:
1. Financial Risk: Hallucinated quantities or amounts could dispatch erroneous vendor
   purchase orders or issue inaccurate billing statements.
2. Data Integrity Risk: A malformed SQL query or prompt injection attempt could trigger
   unindexed table scans, delete entire tables, or overwrite critical customer data.
3. Reputational & Compliance Risk: Automated emails or customer ticket escalations sent
   without human approval violate compliance standards and damage trust.

The Architectural Solution: The "Read-Autonomously, Stage-Writes" Pattern
This project introduces a strict architectural division:
* Autonomous Analytical Boundary (Reads): The agent is granted autonomous read access
  to query schemas, join cross-domain tables, compute runway metrics, and synthesize
  findings without human intervention.
* Staged Transactional Boundary (Writes): Any action that alters state (sending an email,
  creating a purchase order, escalating a ticket, or modifying permissions) is intercepted
  at the runtime level. It is converted into a pending action item staged in a Human
  Clearance Gate, complete with formatted previews and editable parameter payloads.

4. KEY TECHNICAL INNOVATIONS
================================================================================

--------------------------------------------------------------------------------
4.1. AST-Level SQL Guardrail Engine (sqlglot)
--------------------------------------------------------------------------------
Conventional systems rely on regex or keyword blacklists, which are easily bypassed
by multi-line queries, SQL comments (/* ... */), string concatenation, or nested
subqueries.

This project implements an AST Parser utilizing `sqlglot`:
1. Syntactic Verification: Parses incoming SQL into an Abstract Syntax Tree using the
   MySQL dialect. Multiple semicolon-delimited statements are strictly rejected.
2. Prohibited Statement Defense: Checks the AST node type. Expressions of type
   exp.Drop, exp.Alter, exp.Create, exp.Truncate, exp.Grant, or exp.Revoke immediately
   raise a SecurityGuardrailViolation (returning HTTP 403 Forbidden).
3. Table Whitelist Enforcement: Traverses all exp.Table nodes in the AST and ensures
   every referenced table exists in the ALLOWED_TABLES whitelist (24 tables + 4 views).
   Access to system schemas (information_schema, performance_schema, mysql.*) is blocked.
4. Tautology & Mass-Update Protection: For UPDATE and DELETE expressions, an explicit
   WHERE clause is strictly required. Furthermore, tautological expressions like
   "1=1", "TRUE", or "'a'='a'" are parsed and rejected.
5. Automated Clamping: SELECT queries without a LIMIT clause are automatically rewritten
   with LIMIT 100. Queries specifying limits above 500 are clamped down to 500.

--------------------------------------------------------------------------------
4.2. Human-in-the-Loop Clearance Subsystem & Idempotency
--------------------------------------------------------------------------------
When the agent determines that an operational write is necessary, it invokes the
corresponding tool, but execution is safely paused:
1. Deterministic Risk Classification: Risk levels are hardcoded into Python enum
   metadata (READ, LOW_RISK_WRITE, EXTERNAL_COMMUNICATION, FINANCIAL, ACCESS_CONTROL,
   DESTRUCTIVE). Risk is never left to the model's subjective judgment.
2. Staging via PendingAction: The action is saved to the database with status
   "AWAITING_APPROVAL", containing the full payload and a formatted preview.
3. Dual-Key Idempotency: Every staged action receives a cryptographic UUID execution key.
   When an operator approves an action, the key is verified. Once executed, the key is
   invalidated. Repeated clicks or network retries return the cached result rather than
   re-executing the action.
4. Interactive Payload Modification: Operators can open an editing modal in the web UI
   to adjust parameters (e.g., change an email subject or modify purchase order quantity)
   before signing off.
5. Immutable Security Audit Ledger: Every operation, node transition, tool call, human
   decision, and modified payload is recorded in the `audit_events` table.

--------------------------------------------------------------------------------
4.3. LangGraph Multi-Stage State Machine & Visual Observability
--------------------------------------------------------------------------------
The execution pipeline is modeled as a compiled LangGraph `StateGraph(OperationsState)`
with a 2-loop cyclic architecture:
* analyze_node: Evaluates the user request, determines workflow classification,
  extracts parameters, and logs initial micro-steps.
* agent_node: ReAct reasoning loop (Loop 1) where the LLM selects domain tools.
* tools_node: Dispatches autonomous read tools and intercepts consequential writes
  at the Human Clearance Gate.
* validate_node: Deterministic policy and guardrail checks over all staged actions.
* self_correct_node: Remediates violations in Loop 2 before human clearance.
* finalize_node: Pauses for clearance or outputs conversational synthesis.
* Conversational HITL Continuation: Operator follow-up instructions (/instruct)
  resume the state machine dynamically without losing staged context.
* Visual Observability Engine: Deeply instrumented with `langgraph-observe`
  (Source: https://github.com/sreekanthpinnaka/langgraph_observability_tool)
  providing standalone visual DAG topology, node waterfall traces, state diffs,
  token metrics, and tool latencies at http://localhost:8765.


--------------------------------------------------------------------------------
4.4. Dual Execution Engine (LLM Tool-Calling + Deterministic Fallback)
--------------------------------------------------------------------------------
Reliability in production requires graceful degradation:
* Primary Engine: OpenAI (`gpt-4o-mini`) or Google Gemini tool calling with low
  temperature (0.1) for consistent, structured execution plans.
* Deterministic Offline Fallback: If API keys are unconfigured, network timeouts occur,
  or rate limits are reached, the agent catches the error and falls back to an internal
  deterministic simulation engine that processes standard operational intents without
  failing.

5. ENTERPRISE SCHEMA & DATA CATALOG (24 Tables & 4 Views)
================================================================================

The platform operates against a normalized enterprise database spanning 7 operational
domains:

1. Identity & Organization Domain:
   * app_users: Operators and administrators authorized to use the copilot.
   * customers: Client accounts, contract tiers (starter, business, enterprise), billing emails.
   * employees: Internal personnel, job roles, departments, manager reporting hierarchy.
   * software_systems: Corporate infrastructure and apps with sensitivity ratings.

2. Finance & Receivables Domain:
   * invoices: Accounts receivable ledger, amounts, balances due, due dates, statuses.
   * sales_leads: CRM opportunities, deal stages, pipeline values, engagement scores.
   * email_messages: Outbox of staged and transmitted dunning notices and vendor orders.
   * overdue_invoice_candidates (VIEW): Real-time view of invoices overdue by 30+ days.

3. Customer Support & Triage Domain:
   * support_tickets: Customer cases, severities (critical, high, medium, low), routing.

4. Supply Chain, Inventory & Procurement Domain:
   * products: Catalog SKUs, categories, and standard reorder packaging sizes.
   * suppliers: Approved vendors, reliability ratings (1.0 to 5.0), delivery lead times.
   * supplier_products: Vendor price sheets, minimum order quantities (MOQs).
   * inventory: Warehouse stock levels, reserved units, average daily consumption rates.
   * purchase_orders: PO headers, supplier IDs, total amounts, workflow statuses.
   * purchase_order_items: Line items, quantities, unit prices, line totals.
   * inventory_reorder_candidates (VIEW): Products with <= 14 days of stock runway.

5. Security & Access Control Domain (RBAC):
   * access_policies: Role entitlement rules mapping job roles to system permissions.
   * access_requests: Employee privilege requests with business justifications.
   * access_review_queue (VIEW): Pending access requests awaiting compliance review.

6. Meetings & Team Collaboration Domain:
   * meetings: Operational syncs, incident post-mortems, meeting notes.
   * meeting_participants: Employee attendance tracking.
   * action_items: Assigned deliverables, owners, due dates, dependency blockers.

7. Governance & Security Audit Domain:
   * operation_requests: Complete record of agent sessions, prompts, and plans.
   * operation_steps: Granular planned step records and execution statuses.
   * pending_actions: Consequential actions staged at the Human Clearance Gate.
   * approvals: Human operator sign-offs, reviewer IDs, and modified payloads.
   * audit_events: Immutable security audit log tracking tool calls and guardrails.
   * operation_execution_history (VIEW): Aggregated operational KPIs and approval rates.

7. END-TO-END OPERATIONAL PLAYBOOKS & DEMO SCENARIOS
================================================================================

Scenario 1: Accounts Receivable Overdue Invoices
* Prompt: "Find invoices overdue by more than 30 days and prepare reminder emails."
* Execution Flow:
  1. The agent queries `overdue_invoice_candidates`.
  2. Synthesizes delinquent accounts, balances due, and days past due into the Evidence Table.
  3. Formulates dunning notices tailored to customer contract tiers.
  4. Stages `send_email` actions in the Human Clearance Gate.
  5. The operator reviews the email subject/body, edits text if needed, and clicks Approve.

Scenario 2: Inventory Runway & Purchase Order Procurement
* Prompt: "Find inventory likely to run out within 14 days and prepare reorders."
* Execution Flow:
  1. The agent queries `inventory_reorder_candidates`.
  2. Calculates remaining stock runway based on current_stock / average_daily_usage.
  3. Looks up approved vendors and minimum order quantities in `supplier_products`.
  4. Stages `create_purchase_order` actions categorized with Risk Level FINANCIAL.
  5. The operator inspects the total PO cost and authorizes the transaction.

Scenario 3: Critical Support Ticket Escalation
* Prompt: "Review today's support tickets and escalate critical payment issues."
* Execution Flow:
  1. The agent queries `support_tickets` where severity = 'critical' and category = 'payment'.
  2. Identifies impacted enterprise clients.
  3. Stages `escalate_ticket` actions targeted at the Tier-3 engineering lead.
  4. The operator approves the escalation, updating ticket records instantly.

Scenario 4: AST Guardrail Security Testing
* Safe Query: "SELECT customer_code, name, tier FROM customers WHERE tier = 'enterprise';"
  Result: 200 OK, sanitized, auto-clamped with LIMIT 100.
* Attack Query: "DROP TABLE customers;"
  Result: 403 Forbidden ("Destructive statement type Drop is prohibited by guardrails").
* Attack Query: "UPDATE employees SET job_role = 'Admin' WHERE 1=1;"
  Result: 403 Forbidden ("UPDATE statements with unconditional WHERE clauses are rejected").

  Description: Retrieves full state, trajectory stepper steps, findings, and pending actions.

* POST /api/operations/{operation_id}/instruct
  Description: Conversational continuation on staged actions; resumes the LangGraph
               state machine with full conversational memory without losing staged context.
  Body: {"instruction": "Change vendor on the first order to Northwind and set quantity to 200."}
  Response: 200 OK (Updated OperationView with modified plan and staged actions).

* POST /api/operations/{operation_id}/approve
  Description: Executes or rejects staged consequential actions.
  Body: {
    "approved_action_ids": ["uuid-1"],
    "rejected_action_ids": ["uuid-2"],
    "modified_actions": [{"action_id": "uuid-1", "payload": {...}}]

  Response: 200 OK (Updated OperationView with execution results).

  Description: Fetches chronological security audit log events for compliance review.
  Response: 200 OK (List of AuditEventView objects).

10. LOCAL SETUP & QUICK START GUIDE
================================================================================

Prerequisites:
* Python 3.11+
* Node.js 18+ and npm
* Git

Step 1: Start LangGraph Observability Server
1. Clone the observability tool:
   git clone https://github.com/sreekanthpinnaka/langgraph_observability_tool.git
   cd langgraph_observability_tool
2. Install dependencies:
   pip install -e .
3. Launch standalone observability server:
   langgraph-observe
   # Visual trace dashboard: http://localhost:8765

Step 2: Start FastAPI Backend
1. Navigate to the backend directory:
   cd gemini/backend
2. Create and activate a virtual environment:
   python -m venv .venv
   # Windows:
   .venv\Scripts\Activate.ps1
   # macOS/Linux:
   source .venv/bin/activate
3. Install dependencies:
   pip install --upgrade pip
   pip install -r requirements.txt
4. Setup environment:
   cp .env.example .env
   # Edit .env with your OpenAI/Gemini key and OBSERVE_SERVER_URL=http://localhost:8765
5. Launch FastAPI server:
   uvicorn app.main:app --reload --port 8000
   # Health check: http://localhost:8000/api/health
   # Swagger docs: http://localhost:8000/docs

Step 3: Start React Frontend Client
1. Open a new terminal and navigate to the frontend directory:
   cd gemini/frontend
2. Install dependencies:
   npm install
3. Setup environment:
   cp .env.example .env
   # Ensure VITE_API_BASE_URL=http://localhost:8000/api
4. Launch Vite development server:
   npm run dev
5. Open your browser at:
   http://localhost:5173

11.4. Technical Interview Defense & System Design Q&A
--------------------------------------------------------------------------------

Q1: "Why did you use LangGraph instead of a basic ReAct loop or standard LangChain chain?"
A: "A standard ReAct agent runs an unconstrained while-loop that mixes model reasoning, tool
execution, and state updates. In an enterprise system, you need deterministic state boundaries.
With LangGraph, I structured the agent as an explicit finite state machine: `analyze` classifies
intent and normalizes inputs, `execute` runs tool calling, and `finalize` checks if consequential
actions were staged. This makes the Human Clearance Gate an explicit graph pause point rather
than an ad-hoc interrupt, and allows distributed tracing to observe exact node latencies."

Q2: "Why use an Abstract Syntax Tree (AST) with sqlglot instead of regular expressions?"
A: "Regular expressions are notoriously easy to bypass in SQL. Attackers can inject inline
comments (e.g., 'SEL/*comment*/ECT'), use line breaks, hex encoding, or bury malicious subqueries
inside string literals. sqlglot parses the entire query into a formal syntax tree. This allows us
to inspect AST node types directly (like exp.Drop or exp.Table), verify table names against a
strict whitelist, ensure non-tautological WHERE clauses on updates, and inject LIMIT clauses
directly into the parsed syntax tree before compiling back to sanitized SQL."

Q3: "How does the system guarantee idempotency when an operator approves an action?"
A: "When the agent stages an action, the backend generates an immutable UUID execution_key
stored in the database. When the operator submits their approval from the frontend, the request
must present this execution key. The approval endpoint runs inside an atomic database transaction.
It verifies that the action is still in 'AWAITING_APPROVAL' status, executes the action, updates
the status to 'COMPLETED', and commits the audit log. Any duplicate click or replayed request
sees that the action is already completed and safely aborts."

Q4: "How does the agent handle LLM API failures or rate limits?"
A: "Resilience is built directly into the execution service. The agent loop wraps the LLM tool
calling in a try/except block. If an API key is missing, network times out, or rate limits are hit,
the system logs a fallback micro-step and hands off execution to an internal deterministic agent
simulation engine. This engine extracts intent using rule-based pattern matching and executes the
corresponding database queries, ensuring the user interface never crashes or displays a blank screen."
